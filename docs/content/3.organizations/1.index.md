Better Auth's [Organization plugin](https://better-auth.com/docs/plugins/organization), as it is, for whatever your
app uses organizations for: teams, workspaces, companies.

## Turning it on

::steps{level="3"}

### Enable it

```ts [nuxt.config.ts]
export default defineNuxtConfig({
  betterAuthUi: {
    organization: { enabled: true }
  }
})
```

### Run Better Auth's migrations

The plugin adds `organization`, `member` and `invitation` tables, and the session's `activeOrganizationId`. Teams and
dynamic roles add their own tables too.

### Send invitations by email (optional)

Invitations are emailed when [`emails.send`](/customization/emails) is set, with the `organization-invitation`
template. Their links can be copied either way.

::

## What people get

### On the account page

An "Organizations" tab with their organizations (and their teams in each), the active one marked, switching to
another, and creating one: a name, a slug made from it and checked as they type, and your own fields. Invitations sent
to them show at the top, with Accept and Decline. Better Auth lists them only for a verified email.

### The organization's page

`/organization/<id>`, for signed-in members. Each part shows to those whose role allows it, from Better Auth's own
permission check, so your roles and dynamic roles count:

| Tab | What it does | Permissions |
| --- | --- | --- |
| General | Name, slug, logo and your fields; leaving; deleting | `organization:update`, `organization:delete` |
| Members | A page at a time, with your member fields; changing roles (several each); removing | `member:update`, `member:delete` |
| Invitations | Invite by email with roles, a team and your fields; send again, copy the link, cancel | `invitation:create`, `invitation:cancel` |
| Teams | Create, rename and remove teams; add and remove members; set your active team | `team:*` |
| Roles | The app's roles and what each allows; the organization's own roles | `ac:*` |
| SSO | The organization's identity providers, for owners and admins | See [Single sign-on](/organizations/sso) |

### The invitation page

The email's link (`/accept-invitation/<id>`, signed in) shows who invited them, to which organization and as what,
then Accept or Decline.

## In your app

The module gives you a composable and a component for your own layout:

::code-group
```vue [Switcher]
<template>
  <!-- Switch organization and team, open its page, create one. -->
  <AuthOrganizationSwitcher />
</template>
```

```vue [Composable]
<script setup lang="ts">
// The active organization, with its members, server-rendered and following the session.
const { organization, activeTeamId } = useActiveOrganization()
</script>
```
::

Check permissions on your server with Better Auth's own API:

```ts [server/api/projects.post.ts]
export default defineEventHandler(async (event) => {
  const auth = serverAuth(event)
  const { success } = await auth.api.hasPermission({
    headers: event.headers,
    body: { permissions: { project: ['create'] } }
  })
  if (!success) throw createError({ statusCode: 403 })
  // The member's role in the active organization, if you need it:
  const { role } = await auth.api.getActiveMemberRole({ headers: event.headers })
})
```

## In the admin

- An "Organizations" page lists every organization, with a search by name and member counts.
- Each organization's page shows its members (linking to their user pages), pending invitations, teams and own roles.
- A user's page lists their organizations.

Staff who can update users (`user: update`) change organizations through the calls Better Auth allows from the server,
without a member's session. Its hooks and limits apply, and each change is recorded in the audit log:

| Staff can | Through Better Auth's |
| --- | --- |
| **Create an organization** for a user, who becomes its owner | `createOrganization` |
| **Add a member**, with roles and a team | `addMember` |
| **Create and remove teams** | `createTeam`, `removeTeam` |

Better Auth needs one of the organization's members for everything else: renaming or deleting it, changing members'
roles or removing them, invitations, and its own roles. With
[impersonation](/admin/users#signing-in-as-a-user) on, the organization's admin page offers **Sign in as** its owner,
which opens the organization's own page as them. The impersonation is recorded in the audit log, and the banner leads
back.

## Options

::field-group
  ::field{name="enabled" type="boolean" default="false"}
  ::

  ::field{name="page" type="string" default="'/organization'"}
  The organization's own page: `<page>/<organization id>`.
  ::

  ::field{name="invitationPage" type="string" default="'/accept-invitation'"}
  The invitation page: `<page>/<invitation id>`.
  ::

  ::field{name="allowUserToCreateOrganization" type="boolean" default="true"}
  Whether users can create organizations.
  ::

  ::field{name="organizationLimit" type="number"}
  Organizations a user can create. Unlimited by default.
  ::

  ::field{name="membershipLimit" type="number" default="100"}
  Members an organization can have.
  ::

  ::field{name="creatorRole" type="'owner' | 'admin'" default="'owner'"}
  The role of whoever creates an organization.
  ::

  ::field{name="invitationExpiresIn" type="number" default="172800"}
  Seconds an invitation lasts (48 hours).
  ::

  ::field{name="invitationLimit" type="number" default="100"}
  Pending invitations a user can send.
  ::

  ::field{name="requireEmailVerificationOnInvitation" type="boolean" default="false"}
  Invitations need a verified email to see, accept or decline.
  ::

  ::field{name="cancelPendingInvitationsOnReInvite" type="boolean" default="false"}
  Inviting someone again cancels their pending invitation.
  ::

  ::field{name="disableOrganizationDeletion" type="boolean" default="false"}
  Nobody can delete an organization.
  ::

  ::field{name="teams" type="boolean | object" default="false"}
  Teams within organizations. `{ maximumTeams, maximumMembersPerTeam, allowRemovingAllTeams }` to set limits.
  ::

  ::field{name="statements" type="Record<string, string[]>"}
  Your own resources and actions. See [Roles and permissions](/organizations/roles).
  ::

  ::field{name="roles" type="Record<string, Record<string, string[]>>"}
  Organization roles and their permissions. See [Roles and permissions](/organizations/roles).
  ::

  ::field{name="dynamicRoles" type="boolean | object" default="false"}
  Organizations create their own roles. See [Roles and permissions](/organizations/roles#roles-each-organization-makes).
  ::

  ::field{name="schema" type="object"}
  Better Auth's schema options: table and field names, and your own fields (`additionalFields`) on `organization`,
  `member`, `invitation`, `team` and `organizationRole`. The organization's page shows and edits them.
  ::

  ::field{name="serverOptions" type="string"}
  A file with more of the plugin's options, for those that are functions. See below.
  ::
::

### Options that are functions

Some of Better Auth's options are functions, like `organizationHooks`, or `organizationLimit` worked out per user.
They can't go in `nuxt.config.ts`, so put them in a file and point `serverOptions` at it:

::code-group
```ts [nuxt.config.ts]
export default defineNuxtConfig({
  betterAuthUi: {
    organization: {
      enabled: true,
      serverOptions: './server/auth/organization.ts'
    }
  }
})
```

```ts [server/auth/organization.ts]
export default {
  organizationHooks: {
    afterCreateOrganization: async ({ organization }) => {
      console.info(`Organization created: ${organization.name}`)
    }
  }
}
```
::

Its options are added last, so they win over the module's. It's loaded with your auth config, also at build time, so
keep Nitro-only imports out of its top level.

::note
The pages use Better Auth's words (organization, owner, admin, member). Call organizations "teams" or anything else
with [`messages`](/customization/languages#your-own-words).
::
